### **项目计划书：基于 The Graph 的 AAVE 用户健康因子历史分析与调仓策略研究**

#### **1. 项目愿景与目标**

* **最终愿景**: 开发一个自动化的数据分析模型，该模型能够识别导致 AAVE 用户健康因子（Health Factor, HF）剧烈变化的关键操作和市场条件，为构建智能调仓机器人（例如，在 HF 过低时自动偿还部分债务或补充抵押品）提供数据驱动的决策依据。
* **本期目标**: 成功搭建一个数据处理管道（Pipeline）。该管道能够：
    1.  监控或获取指定用户的 AAVE 交易历史。
    2.  对每一笔关键交易（如 `Borrow`, `Withdraw`），精确提取其发生**前**和**后**的用户账户状态（资产、负债）和市场状态（资产价格、风险参数）。
    3.  基于提取的数据，计算并记录交易前后的健康因子。
    4.  将结果结构化地存储，以供后续分析。

#### **2. 核心逻辑与技术选型**

* **核心逻辑**: 区块链的状态是离散且不可变的。一笔交易 `Tx` 发生在区块 `N`，它会改变协议的状态。因此，在区块 `N-1` 的状态是“交易前”，而在区块 `N` 的状态是“交易后”。我们将利用 The Graph 的 `block: { number: ... }` 查询功能，像“时间机器”一样精确访问这两个历史时刻的状态。
* **技术选型**:
    * **数据源**: The Graph Protocol。
    * **目标子图 (Subgraph)**: Aave V3 on Ethereum Mainnet Subgraph。
    * **编程语言**: Python 3.x (因其强大的数据处理库 `pandas` 和网络请求库 `requests` / `gql`)。
    * **数据存储**: 初期使用 CSV 文件或 SQLite 数据库，方便快速原型设计和分析。

#### **3. 主要挑战**

1.  **健康因子的链下计算**: The Graph 子图本身不提供 `healthFactor`。我们必须查询所有必需的“原材料”（用户各资产的余额、各资产的美元价格、各资产的清算阈值），然后在我们的 Python 脚本中复现官方的健康因子计算公式。
2.  **数据查询的复杂性**: 为了在特定区块获取完整的状态快照，我们需要构建一个相对复杂的 GraphQL 查询，它能同时抓取用户数据、市场配置数据和价格数据。
3.  **异步与速率限制**: 在大规模分析时，需要处理对 The Graph 公共节点 API 的请求频率，避免被封禁。

### **4. 项目实施阶段 (Step-by-Step Plan)**

我们将项目分解为六个可管理的阶段：

#### **第一阶段：环境准备与基础探索 (入门)**

* **任务**:
    1.  安装 Python 环境及必要的库 (`requests`, `gql`, `pandas`)。
    2.  熟悉 AAVE V3 Subgraph 的在线浏览器 (Playground)。我们将在这里手动测试我们的第一个 GraphQL 查询。
    3.  理解 Subgraph 的基本结构（Schema），了解 `User`, `UserReserve`, `Reserve`, `PriceHistoryItem` 等核心实体的含义。
* **产出**: 能够在 The Graph Playground 中，成功执行一个简单的查询（例如，查询某个用户的当前所有头寸）。

#### **第二阶段：获取目标交易列表 (定位)**

* **任务**:
    1.  编写 Python 脚本，查询特定用户地址的所有交易事件（如 `Borrow`, `Withdraw`, `LiquidationCall` 等）。
    2.  从查询结果中，提取出每笔交易的**交易哈希 (ID)** 和 **区块号 (Block Number)**。
* **产出**: 一个包含 `(交易哈希, 区块号, 交易类型)` 的列表或数据框（DataFrame），这将是我们后续分析的“任务清单”。

#### **第三阶段：构建“状态快照”查询函数 (核心)**

* **任务**:
    1.  设计一个复杂的 GraphQL 查询语句。这个查询需要能接受 `user_address` 和 `block_number` 作为变量。
    2.  该查询需要一次性返回：
        * 指定用户在该区块的所有 `UserReserve` 数据（抵押品余额、债务余额）。
        * 这些资产对应的 `Reserve` 数据（清算阈值 `liquidationThreshold`）。
        * 这些资产对应的 `Price` 数据（以 ETH 或 USD 计价的价格）。
    3.  在 Python 中，封装一个函数 `get_state_snapshot(user_address, block_number)`，该函数负责发送上述查询并返回结构化的 JSON 数据。
* **产出**: 一个可复用的 Python 函数，它是我们整个项目的“发动机”。

#### **第四阶段：实现健康因子计算器 (计算)**

* **任务**:
    1.  基于第三阶段获取的数据，在 Python 中实现健康因子的计算逻辑。
    2.  公式：$HF = \frac{\sum (CollateralBalance \times Price \times LiquidationThreshold)}{\sum (DebtBalance \times Price)}$
    3.  封装一个函数 `calculate_health_factor(state_snapshot_data)`，输入状态快照数据，输出一个浮点数（健康因子）。
* **产出**: 一个精确的健康因子计算函数。

#### **第五阶段：组装数据处理管道并存储 (执行与固化)**

* **任务**:
    1.  编写主脚本，遍历第二阶段生成的“任务清单”。
    2.  对于清单中的每一笔交易（区块号为 `N`）：
        * 调用 `get_state_snapshot()` 函数两次，分别获取区块 `N` 和 `N-1` 的状态。
        * 调用 `calculate_health_factor()` 函数两次，计算出 `hf_before` 和 `hf_after`。
        * 记录当时的市场状况（例如关键资产的价格）。
    3.  将所有计算结果（交易哈希, 区块号, 交易类型, hf_before, hf_after, 市场状况快照）追加到一个 CSV 文件或数据库中。
* **产出**: 一个包含所有分析结果的、结构化的历史数据集。

#### **第六阶段：数据分析与模型构思 (洞察与升华)**

* **任务**:
    1.  使用 `pandas` 对第五阶段生成的数据集进行探索性数据分析（EDA）。
    2.  分析哪些类型的交易、在什么样的市场环境下，最容易导致 HF 骤降。
    3.  构思调仓模型的触发条件和响应动作。例如：
        * **触发器**: `Borrow` 操作后，`hf_after` < 1.5。
        * **潜在动作**: 计算偿还占总债务10%的贷款后，HF能恢复到多少；或者，计算补充多少价值的抵押品，能使HF恢复到1.8。
* **产出**: 一份数据分析报告，以及调仓模型的初步伪代码或逻辑流程图。
